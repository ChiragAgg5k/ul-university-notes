**One grid and two phases.** A burning cell may be visited before a neighbouring tree. Clearing it immediately would hide the fire from that tree. During the decision phase, `BURNING_OUT` therefore still means burning to a neighbour. A newly marked `TREE_IGNITING` first becomes a source of fire at the next step. Boundary locks could order individual accesses, but would still need a way to preserve the old state. Updating alternating checkerboard colours also allows one colour to see changes from the other. The temporary states preserve synchronous steps with one writer per cell. (ForestFire.java, lines 17–25, 90–104, 109–125 and 137–149.)

**Row blocks and chunk size.** The default assigns one consecutive block of complete rows to each worker. Columns would split each row among workers, while cyclic rows would place many more neighbouring rows under different owners. Within a block, a worker traverses each row in array order and shares just its two edge rows with neighbouring blocks for reads. Static assignment requires no shared counter. Dynamic assignment lets a worker that finishes early claim another chunk, at the cost of an atomic operation per claim (Oracle, 2026, AtomicInteger.getAndIncrement). Section 6.5 compares four and sixteen chunks per worker. (ForestFireParallel.java, lines 114–129 and 141–148.)

**Reusable barrier.** The design uses the reusable rendezvous specified by the Java SE 27 CyclicBarrier API (Oracle, 2026). The first rendezvous lets all workers finish reading neighbours before any starts committing. The second makes all committed byte writes visible before the next round of neighbour reads. A mutex protects a critical section, whereas this dependency requires every worker to finish a phase. A semaphore counts permits. Using it for a repeating phase boundary would require tracking arrivals and releasing the group on every round. A fixed group can reuse one cyclic barrier; a fresh group per phase uses thread termination and joins to establish the same ordering. Section 6.5 measures the cost of that alternative. (ForestFireParallel.java, lines 168–176 and 193–212.)

**Separate recorder.** The two recorder variants use the queue and permit operations specified for LinkedBlockingQueue and Semaphore (Oracle, 2026). Workers count their cells as they commit them. Each sends the step number and three totals through a queue, allowing the recorder to aggregate by step while workers continue. A barrier action would run on a worker. A separate scanning recorder satisfies the task requirement but needs a stable grid: it waits for one committed permit per worker, scans every cell, then releases the waiting workers. (ForestFireParallel.java, lines 87–110 and 131–137.)

**Randomness.** A draw depends on the seed, step, row and column. Moving a row to another worker therefore preserves its draws. With a generator per worker, changing the partition changes which sequence a cell receives. With a single shared generator, scheduling determines draw order and workers contend over the generator state. Section 6.6 measures the shared-generator alternative. (ForestFire.java, lines 90–95 and 155–166; ForestFireParallel.java, lines 79–84.)

**Wrapped neighbours.** For the top-left cell, the offset one row up and one column left leads to the bottom-right cell. Adding the dimension before taking the remainder implements this rule on either axis. Precomputed neighbour indices could remove remainder operations from the inner loop at the cost of extra tables. The implementation uses the direct formula; this decision was assessed by inspection. (ForestFire.java, lines 109–125.)

### Foster’s checklist applied to the forest

The four stages follow Foster (1995, chapter 2) and Alrimawi (2026, Lecture 3). Slide numbers refer to the printed numbers in the course deck `Lecture 3 W03_Parallel Algorithm.pdf`.

**Partitioning (Lecture 3, slide 28).** At cell granularity, each phase has a million tasks on a 1000 × 1000 grid, well above ten per worker even at eight workers. Doubling the side length quadruples the task count. Every task updates one cell, but its cost varies: a tree can examine eight neighbours, while a burning cell takes a single transition. Rows, columns and tiles are alternative ways to group those primitive tasks (ForestFire.java, lines 92–103 and 109–125).

**Communication (slide 31).** Each static worker sends one count message and reaches two barriers per step. Cell reads can proceed concurrently and reach at most eight neighbours. Only a block’s top and bottom rows need values from adjacent blocks. Counts converge on a single recorder and each barrier waits for the last arrival, so the communication is only partly concurrent (ForestFireParallel.java, lines 103–109, 136 and 201–210).

**Agglomeration (slide 34).** Combining cells into complete rows keeps consecutive column accesses in the same Java array. Equal-sized blocks give workers similar cell counts and identical numbers of hand-offs, although their neighbour-search costs can differ. At fixed worker count the default always has one block per worker: larger grids grow the blocks. The shared row-range methods keep this grouping cheap to implement in both runners (ForestFireParallel.java, lines 114–129 and 141–148).

**Mapping (slide 38).** Static mapping assigns one block to each worker. Dynamic mapping lets any worker claim the next block from an atomic counter. At 1000 rows and eight workers, static blocks have 125 rows; 32 chunks have 31 or 32 rows each, and 128 chunks have 7 or 8. The respective eight-worker speedups were 6.02×, 6.42× and 6.81× in section 6.5. The finer chunks improved the median despite more atomic claims. The experiment measures that combined effect; it does not establish how much time workers spent contending for the counter (ForestFireParallel.java, lines 76, 120–129 and 141–148).
